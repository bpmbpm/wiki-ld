## answer 1

Да, ваша оценка верна: **Bank Ontology/FIBO нельзя брать как верхнеуровневую онтологию предприятия**. Она хорошо описывает финансовые продукты, договоры, стороны, кредиты и инструменты, но не охватывает HR, ИТ, закупки, недвижимость, проектную деятельность, риск-менеджмент и корпоративное управление как равноправные направления. ## Верхние классы

Практичный верхний уровень для wiki банка:

```text
Предприятие
├── Организация
│   ├── Юридическое лицо
│   ├── Оргструктура / подразделение
│   ├── Роль / должность
│   └── Персона
├── Стратегия и цели
│   ├── Цель
│   ├── KPI
│   ├── Инициатива
│   └── Риск
├── Бизнес-способность
├── Бизнес-процесс
├── Продукт / услуга
├── Клиент / контрагент
├── Ресурс
│   ├── Персонал
│   ├── Помещение
│   ├── Оборудование
│   └── Финансовый ресурс
├── Информация / данные
│   ├── Бизнес-объект
│   ├── Документ
│   ├── Система
│   └── Набор данных
├── ИТ-система / приложение
├── Нормативное требование
├── Проект / изменение
└── Банковский домен
    ├── Кредитный продукт
    ├── Счет
    ├── Платеж
    ├── Обеспечение
    └── Финансовый инструмент
```

Это соответствует логике TOVE: предприятие моделируется через деятельность, ресурсы, организацию, продукты, цели и ограничения, а не только через финансовые сущности. [hal](https://hal.science/hal-00577040v1/file/ZdravkoviA_et_al.pdf)

## Базовый принцип wiki

Страница wiki должна представлять **экземпляр понятия онтологии**, а не произвольный документ.

Правило именования:

```text
[Тип] — [Имя экземпляра]
```

Примеры:

- `Организация — Департамент ИТ`
- `Бизнес-процесс — Открытие расчетного счета`
- `Бизнес-способность — Управление кредитным риском`
- `Продукт — Корпоративный кредит`
- `ИТ-система — АБС`
- `Данные — Договор кредитования`
- `Требование — 115-ФЗ: идентификация клиента`

Тип страницы фиксируется в ее метаданных, а не только в названии.

## Структура пространства

Не делайте дерево страниц единственной онтологией: дерево удобно для навигации, но плохо выражает множественные связи. Используйте **неглубокое дерево + типизированные свойства + метки**.

Рекомендуемая структура:

```text
Enterprise Wiki
├── 00. Онтология и правила
│   ├── Словарь классов
│   ├── Словарь предикатов
│   ├── Шаблоны страниц
│   └── Правила именования
├── 10. Организация
├── 20. Стратегия и цели
├── 30. Процессы
├── 40. Продукты и клиенты
├── 50. Данные и документы
├── 60. ИТ и приложения
├── 70. Ресурсы
├── 80. Требования и риски
└── 90. Банковский домен
```

Дерево задает **первичную принадлежность** страницы: например, процесс «Открытие расчетного счета» лежит в `30. Процессы`, хотя связан с подразделениями, системами, клиентами, продуктами и требованиями.

## Как делать предикатные связи

Гиперссылка в Confluence действительно семантически бедна: она означает лишь «упомянута/связана». Решение — не пытаться превратить каждую ссылку в RDF-предикат, а **вынести типизированные связи в структурированный блок свойств страницы**.

### Шаблон страницы: `Бизнес-процесс`

В начале страницы размещается макрос **Page Properties**:

| Свойство | Значение |
|---|---|
| `Тип` | `Бизнес-процесс` |
| `Код` | `BP-RC-001` |
| `Владелец` | `[Организация — Департамент операционного сопровождения]` |
| `Исполнитель` | `[Роль — Операционист]` |
| `Входит в процесс` | `[Бизнес-процесс — Обслуживание корпоративных клиентов]` |
| `Реализует способность` | `[Бизнес-способность — Открытие счетов]` |
| `Использует систему` | `[ИТ-система — АБС]` |
| `Работает с данными` | `[Данные — Договор банковского счета]` |
| `Требование` | `[Требование — 115-ФЗ: идентификация клиента]` |
| `Продукт` | `[Продукт — Расчетный счет]` |
| `Статус` | `Действует` |

Каждая строка правой колонки — это **предикат**: `использует систему`, `реализует способность`, `работает с данными`, `требование`. Гиперссылка здесь остается техническим носителем связи, но ее смысл задан именем свойства. Confluence позволяет создавать такие таблицы свойств и затем собирать их в отчеты по заданной метке. [apqc](https://www.apqc.org/resource-library/resource-listing/apqc-process-classification-framework-pcf-cross-industry-pdf-8)

### Пример: предикатная модель

```text
Бизнес-процесс: Открытие расчетного счета

  выполняется_ролью        → Операционист
  принадлежит_подразделению → Департамент операционного сопровождения
  реализует_способность     → Открытие счетов
  использует_систему        → АБС
  обрабатывает_объект       → Договор банковского счета
  подчиняется_требованию    → 115-ФЗ
  поддерживает_продукт      → Расчетный счет
```

Это уже почти граф `субъект — предикат — объект`, реализованный средствами обычной wiki.

## Роль меток

Метки Confluence не должны заменять классы онтологии. Разделите их назначение:

| Механизм | Что кодирует | Пример |
|---|---|---|
| Тип страницы в Page Properties | Класс онтологии | `Тип = Бизнес-процесс` |
| Метка типа | Быстрая фильтрация и отчеты | `ont-process` |
| Метка домена | Принадлежность направлению | `domain-it`, `domain-risk`, `domain-retail` |
| Метка жизненного цикла | Статус знания | `status-draft`, `status-approved`, `status-retired` |
| Метка критичности | Управленческий приоритет | `critical`, `regulated`, `confidential` |
| Метка версии/ревизии | Контроль изменений | `rev-2026-q4` |

Например, страница процесса получает метки:

```text
ont-process
domain-retail
domain-compliance
status-approved
regulated
```

Метки особенно полезны для **массовых выборок**: Page Properties Report может собрать все страницы с заданной меткой и показать их свойства в единой таблице. [confluence.atlassian](https://confluence.atlassian.com/conf100/page-properties-macro-1627457216.html)

## «Раскраска» данных

В Confluence есть несколько уровней визуальной семантики:

1. **Метки** — для фильтрации, отчетов и автоматических списков.
2. **Page Properties** — для формальных атрибутов и предикатов.
3. **Status macro / цветовые бейджи** — для жизненного цикла: черновик, согласовано, устарело.
4. **Панели и цветовое оформление** — для визуального выделения класса страницы или уровня критичности.
5. **Шаблоны страниц** — для гарантии одинакового набора свойств у однотипных объектов.
6. **Page Properties Report** — для «представлений» онтологии: реестры процессов, систем, требований, рисков.

Не используйте цвет как единственный носитель смысла: цвет должен дублировать формальное свойство, например `Статус = Устарело` плюс красная панель.

## Минимальный словарь предикатов

Начните не с сотен отношений, а с 15–25 устойчивых предикатов:

| Предикат | Субъект → Объект | Пример |
|---|---|---|
| `входит в` | Процесс → Процесс | Открытие счета → Обслуживание клиента |
| `выполняется ролью` | Процесс → Роль | Процесс → Операционист |
| `принадлежит подразделению` | Процесс → Подразделение | Процесс → Департамент |
| `реализует способность` | Процесс → Способность | Процесс → Открытие счетов |
| `использует систему` | Процесс → ИТ-система | Процесс → АБС |
| `обрабатывает данные` | Процесс → Данные | Процесс → Договор |
| `поддерживает продукт` | Процесс → Продукт | Процесс → Расчетный счет |
| `подчиняется требованию` | Любой объект → Требование | Процесс → 115-ФЗ |
| `влияет на риск` | Процесс/система → Риск | Процесс → Операционный риск |
| `является владельцем` | Подразделение/роль → Объект | Департамент → Процесс |
| `состоит из` | Целое → Часть | Процесс → Подпроцесс |
| `заменяет` | Новый объект → Старый объект | Система → Legacy-система |
| `связан с` | Любой → Любой | Только как fallback |

Последний предикат должен быть **запрещен по умолчанию** в формальных разделах; он допустим лишь в черновиках и обсуждениях.

## Методика внедрения

1. **Зафиксировать область.** Выберите 2–3 направления: например, кредитование, ИТ и комплаенс. Не пытайтесь сразу описать весь банк.
2. **Утвердить верхние 10–15 классов.** Используйте предложенную модель TOVE + ArchiMate; банковские классы подключайте только там, где они нужны.
3. **Создать словарь предикатов.** Для каждого предиката определите: субъект, объект, направление, кардинальность, обязательность и пример.
4. **Сделать шаблоны страниц.** Минимальный набор: организация, подразделение, роль, процесс, способность, продукт, система, данные, требование, риск.
5. **Встроить Page Properties в шаблоны.** Тип, код, владелец, статус и связи должны заполняться одинаково.
6. **Ввести метки по соглашению.** Раздельно кодируйте класс, домен, статус и критичность.
7. **Создать реестры-отчеты.** На страницах доменов собирайте Page Properties Report: все процессы, все системы, все требования, все риски.
8. **Провести пилот.** Опишите один сквозной процесс, например «Открытие расчетного счета», со всеми связями до систем, данных, ролей, продукта и требования.
9. **Проверить запросы.** Убедитесь, что можно ответить: «Какие системы затрагивает процесс?», «Какие требования применимы к продукту?», «Кто владелец способности?».
10. **Ввести governance.** Назначьте владельцев классов, правило обязательных свойств, процесс вывода страницы из эксплуатации и периодическую проверку битых или бессмысленных связей.

## Чего не делать

- Не строить дерево страниц как полную онтологию: один объект часто принадлежит нескольким доменам.
- Не использовать произвольные метки вместо контролируемого словаря.
- Не превращать все ссылки в «связан с»: это уничтожает семантику.
- Не начинать с FIBO как корпоративной онтологии: это специализированная финансовая модель, а не модель предприятия. [hal](https://hal.science/hal-00577040v1/file/ZdravkoviA_et_al.pdf)
- Не требовать от Confluence функций графа знаний, если не готовы внедрять плагины, внешнюю knowledge graph-платформу или экспорт свойств в RDF/OWL.

Практически оптимальный вариант: **Confluence как операционный слой знаний и документации, а онтология — как контролируемая модель классов, свойств и предикатов, реализованная через шаблоны, Page Properties и метки**. При необходимости эти же свойства позже можно выгружать в графовую БД или RDF/OWL без перепроектирования содержания wiki. [pubs.opengroup](https://pubs.opengroup.org/architecture/archimate-doc/ts_archimate/chap8.html)

## Целевая модель

Используйте три независимых, но связанных измерения:

| Измерение | Где реализуется | Назначение |
|---|---|---|
| **Дерево страниц** | Иерархия Confluence | Навигация и первичное размещение объекта |
| **Классы и свойства** | Page Properties в шаблонах | Тип объекта, атрибуты, предикатные связи |
| **Метки** | Labels | Фильтрация, отчеты, домены, статус, критичность |

Дерево отвечает на вопрос «где лежит страница», свойства — «что это за объект и с чем он связан», метки — «как его быстро найти и сгруппировать». Confluence поддерживает иерархию родительских и дочерних страниц, а также макрос Page Tree для отображения части или всего дерева пространства. [confluence.atlassian](https://confluence.atlassian.com/conf102/page-tree-macro-1875248498.html)

## Онтологическая основа

Для верхнего уровня банка рекомендую не брать одну онтологию, а собрать профиль из нескольких спецификаций:

| Слой | Спецификация / модель | Ссылка |
|---|---|---|
| Ядро предприятия: деятельность, ресурсы, организация, продукты, цели | **TOVE** | [TOVE Ontologies](https://eil.mie.utoronto.ca/theory/enterprise-modelling/tove/)  |
| Архитектурные сущности и типизированные связи | **ArchiMate 3.2** | [ArchiMate 3.2 Primer](https://meta.linked.archi/docs/guide/archimate/archimate-3.2-modeling-guide/)  |
| Процессная таксономия | **APQC PCF Cross-Industry** | [APQC PCF](https://www.apqc.org/process-frameworks)  |
| Банковские продукты, договоры, клиенты, платежи, кредиты | **FIBO** | [FIBO specification](https://spec.edmcouncil.org/fibo/)  |
| Банковская логическая модель данных | **FIB-DM / Bank Ontology** | [Banking Data Model](https://bankontology.com/banking-data-model/)  |
| Регуляторные требования и комплаенс | **FRO / LKIF** | [FRO tutorial](https://finregont.com/tutorial-chapter2-load-law/)  |

TOVE специально создавалась для моделирования коммерческих и государственных предприятий через организацию, деятельность, ресурсы, продукты, цели, качество, затраты и состояние.  ArchiMate дает типизированные отношения — например, `assignment`, `serving`, `realization`, `access`, — которые удобно переносить в свойства страниц Confluence.

## Шаг 1. Создать пространство и корневые страницы

**Что сделать.** Создайте отдельное пространство `BANK-KNOWLEDGE`, а не размещайте корпоративную модель внутри проектного пространства.

**Как в Confluence.**

1. В боковой панели выберите **Spaces → Create space**.
2. Задайте ключ `BANK` или `BANK-KNOWLEDGE`.
3. Создайте корневую страницу `Банк — Корпоративная база знаний`.
4. Последовательно создайте дочерние страницы `00–90` из схемы выше.
5. Для каждой страницы верхнего уровня добавьте краткое описание: назначение раздела, владелец, статус наполнения.

**Где.** Confluence по умолчанию создает новую страницу дочерней относительно открытой страницы; страницы можно перемещать в дереве при необходимости. [confluence.atlassian](https://confluence.atlassian.com/conf94/create-and-edit-pages-1540721417.html)

**Результат.** Полный контур направлений банка виден сразу, но детализация контролируемая.

## Шаг 2. Создать страницу «Модель классов»

**Что сделать.** Зафиксировать контролируемый список типов объектов: `Организация`, `Подразделение`, `Роль`, `Персона`, `Бизнес-процесс`, `Бизнес-способность`, `Продукт`, `Клиент`, `ИТ-система`, `Данные`, `Документ`, `Требование`, `Риск`, `Проект`.

**Как в Confluence.**

1. Откройте `00.1 Модель классов`.
2. Создайте таблицу:

| Код класса | Название | Определение | Источник онтологии | Обязательные свойства | Шаблон |
|---|---|---|---|---|---|
| `ORG` | Организация | Юридическое или организационное образование банка | TOVE / ArchiMate | Название, тип, владелец | `TPL-ORG` |
| `PROC` | Бизнес-процесс | Повторяемая деятельность, создающая ценность | TOVE / APQC PCF | Владелец, вход, выход, системы | `TPL-PROC` |
| `APP` | ИТ-система | Программный комплекс, поддерживающий процессы | ArchiMate | Владелец, критичность, данные | `TPL-APP` |
| `REQ` | Требование | Нормативное или внутреннее обязательство | FRO / LKIF | Источник, объект применения, контроль | `TPL-REQ` |

3. Для каждого класса добавьте ссылку на страницу-описание и шаблон.

**Где.** Обычная страница в `00.1 Модель классов`; редактирование через **Create → Page** либо создание дочерней страницы.

**Результат.** Единый источник истины по типам объектов wiki.

## Шаг 3. Создать словарь предикатов

**Что сделать.** Определить типизированные связи, которые разрешено использовать в Page Properties.

Предлагаемый стартовый словарь:

| Код предиката | Название | Субъект | Объект | Пример |
|---|---|---|---|---|
| `hasOwner` | Имеет владельца | Любой объект | Подразделение / роль | Процесс → Департамент кредитования |
| `performedByRole` | Выполняется ролью | Процесс | Роль | Оценка кредитоспособности → Кредитный аналитик |
| `belongsToUnit` | Принадлежит подразделению | Процесс / система | Подразделение | Кредитный конвейер → Департамент ИТ |
| `partOf` | Входит в | Процесс / подразделение | Процесс / подразделение | Выдача кредита → Кредитование |
| `realizesCapability` | Реализует способность | Процесс / система | Бизнес-способность | Процесс → Управление кредитным риском |
| `supportsProduct` | Поддерживает продукт | Процесс / система | Продукт | Кредитный конвейер → Корпоративный кредит |
| `usesSystem` | Использует систему | Процесс | ИТ-система | Процесс → АБС |
| `processesData` | Обрабатывает данные | Процесс / система | Данные | Процесс → Кредитная заявка |
| `governedByRequirement` | Подчиняется требованию | Любой объект | Требование | Процесс → 115-ФЗ |
| `mitigatesRisk` | Снижает риск | Контроль / процесс | Риск | Контроль → Кредитный риск |
| `dependsOnSystem` | Зависит от системы | Система / процесс | ИТ-система | Кредитный конвейер → АБС |
| `replaces` | Заменяет | Новый объект | Старый объект | Новая АБС → Legacy-АБС |
| `relatedTo` | Связан с | Любой объект | Любой объект | Только для неформальных связей |

**Как в Confluence.**

1. Откройте `00.2 Словарь предикатов`.
2. Создайте таблицу с колонками: `Код`, `Название`, `Субъект`, `Объект`, `Направление`, `Кардинальность`, `Обязательность`, `Пример`, `Статус`.
3. Добавьте правило: предикат можно использовать в Page Properties только при статусе `Approved`.
4. Запретите `relatedTo` в формальных шаблонах; разрешите его только в черновиках.

**Где.** Отдельная страница `00.2 Словарь предикатов` в разделе `00. Онтология и правила`.

**Результат.** Ссылка перестает быть безликой: связь получает имя, направление и допустимые типы концов.

## Шаг 4. Создать словарь меток

**Что сделать.** Разделить метки по назначению и запретить произвольные метки.

| Группа | Формат | Примеры |
|---|---|---|
| Класс объекта | `ont-*` | `ont-process`, `ont-product`, `ont-system`, `ont-requirement` |
| Бизнес-домен | `domain-*` | `domain-lending`, `domain-it`, `domain-risk`, `domain-hr` |
| Жизненный цикл | `status-*` | `status-draft`, `status-review`, `status-approved`, `status-retired` |
| Критичность | `crit-*` | `crit-high`, `crit-medium`, `crit-low` |
| Регуляторность | `reg-*` | `reg-cbr`, `reg-115fz`, `reg-pci-dss` |
| Версия модели | `rev-*` | `rev-2026-q4` |

**Как в Confluence.**

1. Откройте `00.3 Словарь меток`.
2. Создайте таблицу: `Метка`, `Назначение`, `Когда применять`, `Кто может добавлять`, `Пример`.
3. Укажите, что метка `ont-process` ставится только страницам, у которых `Тип = Бизнес-процесс`.
4. Для каждой метки задайте владельца — например, архитектор или методолог.

**Где.** Метки добавляются на странице через значок меток рядом с хлебными крошками; в шаблоне метки можно задать заранее, и они будут копироваться на все страницы, созданные по этому шаблону. [confluence.atlassian](https://confluence.atlassian.com/doc/create-a-template-296093779.html)

**Результат.** Метки становятся управляемым фасетным поиском, а не набором случайных тегов.

## Шаг 5. Создать шаблоны страниц

**Что сделать.** Для каждого ключевого класса сделать шаблон с обязательным блоком Page Properties.

Минимальный набор шаблонов:

| Код шаблона | Класс | Обязательные свойства |
|---|---|---|
| `TPL-ORG` | Подразделение | Код, родитель, руководитель, домен, статус |
| `TPL-ROLE` | Роль | Подразделение, процессы, системы, компетенции |
| `TPL-PROC` | Бизнес-процесс | Владелец, родительский процесс, роли, системы, данные, продукт, требования |
| `TPL-CAP` | Бизнес-способность | Владелец, домен, поддерживающие процессы, системы |
| `TPL-PROD` | Продукт | Домен, процессы, системы, данные, риски, требования |
| `TPL-APP` | ИТ-система | Владелец, критичность, данные, интеграции, процессы |
| `TPL-DATA` | Данные / бизнес-объект | Владелец, системы, процессы, чувствительность |
| `TPL-REQ` | Требование | Источник, объекты применения, контроли, риск |
| `TPL-RISK` | Риск | Владелец, процессы, системы, контроли |
| `TPL-PROJECT` | Проект | Цель, сроки, процессы, системы, статус |

**Как в Confluence.**

1. Откройте пространство.
2. Перейдите: **Space settings → Look and feel → Templates**.
3. Выберите **Create new template**.
4. Назовите шаблон, например `TPL-PROC — Бизнес-процесс`.
5. Вставьте в начало страницы макрос **Page Properties**.
6. Внутри макроса создайте двухколоночную таблицу без строки заголовка: слева — имена свойств, справа — значения или ссылки-заглушки.
7. Добавьте ниже разделы: «Назначение», «Входы и выходы», «Связанные объекты», «Требования», «Изменения».
8. Добавьте шаблонные метки, например `ont-process`.
9. Сохраните шаблон.

Официальная последовательность создания шаблона: **Space tools → Content Tools → Templates → Create new template**; в шаблоне можно задать метки, которые будут наследоваться создаваемыми страницами. [confluence.atlassian](https://confluence.atlassian.com/doc/create-a-template-296093779.html)

**Результат.** Пользователь не создает «просто страницу», а создает экземпляр известного класса с обязательной структурой.

## Шаг 6. Настроить Page Properties для предикатных связей

**Что сделать.** Превратить связи в именованные строки таблицы свойств.

Пример шаблона `TPL-PROC — Бизнес-процесс`:

| Свойство | Значение |
|---|---|
| `Тип` | `Бизнес-процесс` |
| `Код` | `BP-CR-003` |
| `Владелец` | `[Организация — Департамент кредитования]` |
| `Входит в процесс` | `[Бизнес-процесс — Кредитование корпоративных клиентов]` |
| `Выполняется ролью` | `[Роль — Кредитный аналитик]` |
| `Реализует способность` | `[Бизнес-способность — Оценка кредитного риска]` |
| `Использует систему` | `[ИТ-система — Кредитный конвейер]` |
| `Использует систему` | `[ИТ-система — АБС]` |
| `Обрабатывает данные` | `[Данные — Кредитная заявка]` |
| `Поддерживает продукт` | `[Продукт — Корпоративный кредит]` |

**Как в Confluence.**

1. В шаблоне выберите **Insert → Other macros → Page Properties**.
2. Внутри макроса создайте таблицу из двух колонок.
3. В левой колонке укажите имена свойств — они станут заголовками отчета.
4. В правой колонке вставьте ссылки на соответствующие страницы.
5. Присвойте странице метку `ont-process`.

Page Properties представляет свойства в виде таблицы «ключ — значение»; эти ключи затем используются как колонки в Page Properties Report. 

**Результат.** На странице процесса видна не просто куча гиперссылок, а семантически именованные связи.

## Шаг 7. Создать реестры через Page Properties Report

**Что сделать.** Собрать объекты одного класса в автоматические представления.

Примеры:

- `Реестр бизнес-процессов кредитования`
- `Реестр ИТ-систем`
- `Реестр требований`
- `Реестр рисков`
- `Матрица «Процесс — Система — Данные»`

**Как в Confluence.**

1. Создайте страницу, например `90.1.9 Реестры домена`.
2. Вставьте макрос **Page Properties Report**.
3. В поле **Label** укажите `ont-process`.
4. При необходимости добавьте фильтр **With ancestor** по странице `90.1 Кредитование`, чтобы отчет не захватывал процессы из других доменов.
5. Выберите колонки: `Код`, `Владелец`, `Использует систему`, `Поддерживает продукт`, `Статус`.
6. Сохраните страницу.

Page Properties Report собирает метаданные только со страниц, имеющих заданную метку; фильтр `With ancestor` позволяет ограничить выборку конкретной ветвью дерева. 

**Результат.** Получается «представление» онтологии: не дублирование данных, а автоматическая выборка объектов по классу и домену.

## Шаг 8. Создать навигационные страницы доменов

**Что сделать.** На каждой странице домена сделать обзор, дерево и ключевые реестры.

Пример страницы `90.1 Кредитование`:

1. Вставьте **Page Tree macro** с корнем `90.1 Кредитование`.
2. Добавьте таблицу «Ключевые объекты домена».
3. Добавьте Page Properties Report для процессов с меткой `ont-process`.
4. Добавьте Page Properties Report для продуктов с меткой `ont-product`.
5. Добавьте ссылки на реестры систем, данных, рисков и требований.

**Где.** Макрос **Page Tree** добавляется через редактор страницы и отображает всю или часть иерархии пространства. [confluence.atlassian](https://confluence.atlassian.com/conf102/page-tree-macro-1875248498.html)

**Результат.** Домен становится не папкой, а рабочим порталом: обзор, объекты, связи и реестры.

## Шаг 9. Настроить правила именования

**Что сделать.** Зафиксировать единый формат заголовков и кодов.

## 2. Как устранить дублирование

Проблема с `40. Бизнес-процессы` и `90. Банковский домен` реальна: процесс «Выдача кредита» нельзя размещать в двух местах как два разных объекта.

Решение — принцип **один объект — одна каноническая страница**.

| Раздел | Роль | Содержимое |
|---|---|---|
| `A4. Бизнес-процессы` | Каноническое размещение процессов | Полные страницы процессов: свойства, связи, описание, версия |
| `A9. Банковские продукты и операции` | Доменное представление | Не копии процессов, а обзоры, реестры и ссылки на канонические страницы |
| `A6. ИТ и архитектура` | Каноническое размещение систем и интеграций | Полные страницы систем |
| `A4. Бизнес-процессы / ИТ-процессы` | Каноническое размещение ИТ-процессов | Полные страницы процессов управления изменениями, инцидентами и т. д. |

То есть **`A9` — это не еще одна ветка процессов**, а «линза» на объекты, размещенные в `A3`, `A4`, `A5`, `A6`, `A8`.

Пример:

```text
A4. Бизнес-процессы
└── Кредитование
    └── Бизнес-процесс — Выдача кредита      ← каноническая страница

A9. Банковские продукты и операции
└── Кредитование
    ├── Обзор домена «Кредитование»
    ├── Реестр кредитных продуктов
    ├── Реестр кредитных процессов            ← Page Properties Report
    ├── Реестр видов обеспечения
    └── Реестр кредитных рисков
```

Страница `Бизнес-процесс — Выдача кредита` существует **один раз**, в `A4`. В `A9` она отображается автоматически через метку `ont-process` и фильтр по домену `domain-lending`. Page Properties Report собирает свойства страниц по заданной метке и может ограничивать выборку ветвью дерева через фильтр `With ancestor`. [confluence.atlassian](https://confluence.atlassian.com/conf90/page-properties-report-macro-1425052653.html)

## 4. Как связаны четыре механизма

Вы правильно выделили четыре сущности:

```text
Дерево страниц Confluence
        ↓ размещает
Модель классов
        ↓ определяет тип страницы
Шаблон страницы + Page Properties
        ↓ реализует
Словарь предикатов
        ↓ индексируется через
Словарь меток → Page Properties Report
```

### Дерево страниц

Дерево — это **навигация и первичное размещение**. Оно отвечает на вопрос: «Где канонически лежит объект?»

Оно не является полной онтологией, потому что один объект может относиться к нескольким доменам: кредитный процесс связан с кредитованием, рисками, ИТ и комплаенсом.

### Модель классов

Модель классов отвечает: «Что это за страница?»

Пример:

```text
Страница: Бизнес-процесс — Выдача кредита
Класс: Бизнес-процесс
```

Класс задает:

- обязательный шаблон страницы;
- обязательные свойства;
- допустимые типы связанных объектов;
- метку класса, например `ont-process`.

### Словарь предикатов

Словарь предикатов отвечает: «Как именно этот объект связан с другим?»

Пример:

```text
Бизнес-процесс — Выдача кредита
    использует систему       → ИТ-система — АБС
    выполняется ролью        → Роль — Кредитный менеджер
    поддерживает продукт     → Продукт — Корпоративный кредит
```

Здесь:

- **субъект** — страница, на которой заполнен Page Properties;
- **предикат** — имя строки в левой колонке Page Properties;
- **объект** — гиперссылка в правой колонке Page Properties.

То есть да: **субъектом по умолчанию выступает сама страница**, к которой относится блок Page Properties. Поэтому в самой таблице не нужно повторять «субъект»: он уже задан заголовком и типом страницы. Page Properties и Page Properties Report работают в паре: первый хранит свойства на странице, второй собирает их в сводные таблицы по метке. [confluence.atlassian](https://confluence.atlassian.com/conf90/page-properties-report-macro-1425052653.html)

### Словарь меток

Метки — это **индекс и фасеты поиска**, а не классы и не предикаты.

Они отвечают на вопросы:

- «Покажи все бизнес-процессы» — `ont-process`;
- «Покажи все объекты кредитования» — `domain-lending`;
- «Покажи все согласованные объекты» — `status-approved`;
- «Покажи критичные ИТ-системы» — `ont-system` + `crit-high`.

## 5. Метки: иерархия через дефис?

**Нет, дефис не создает настоящую иерархию меток в Confluence.** Метки в Confluence плоские: страница может иметь любое количество меток, а метка существует, пока она присвоена хотя бы одной странице; отдельного управления иерархией меток нет. [confluence.atlassian](https://confluence.atlassian.com/doc/add-remove-and-search-for-labels-136419.html)

Запись `domain-lending` — это просто **одно плоское имя метки**, выбранное по соглашению об именовании. Она не является дочерней меткой `domain`.

Поэтому иерархию меток нужно моделировать одним из двух способов.

### Вариант A: префиксная конвенция

```text
ont-process
ont-product
ont-system

domain-lending
domain-it
domain-risk

status-draft
status-approved

crit-high
crit-medium
```

Это удобно, но `domain-lending` и `domain-retail` — независимые метки. Confluence не знает, что обе принадлежат группе `domain`.

### Вариант B: несколько независимых фасетов

Это правильнее. Не пытайтесь сделать одну иерархию меток; используйте несколько ортогональных наборов:

| Фасет | Метки | Вопрос |
|---|---|---|
| Класс | `ont-process`, `ont-product`, `ont-system` | Что это? |
| Домен | `domain-lending`, `domain-it`, `domain-risk` | К какому направлению относится? |
| Статус | `status-draft`, `status-approved`, `status-retired` | Каков жизненный цикл? |
| Критичность | `crit-high`, `crit-medium`, `crit-low` | Насколько важен объект? |
| Регуляторность | `reg-cbr`, `reg-115fz` | Какое регулирование затрагивает? |

Тогда страница процесса может иметь сразу:

```text
ont-process
domain-lending
domain-risk
status-approved
crit-high
```

Это не «иерархия меток», а **пересечение фасетов**. Confluence поддерживает несколько меток на одной странице, и страница появляется во всех соответствующих категориях. [confluence.atlassian](https://confluence.atlassian.com/conf95/organize-your-space-1573749986.html)

```text
    │
    ├── B6. Правила связывания объектов
    │   Онтология: кардинальности, направления, обязательность предикатов
    │
    ├── B7. Реестры и представления
    │   Онтология: проекции онтологии через Page Properties Report
    │
    └── B8. Governance и журнал изменений модели
        Онтология: управление версией метамодели
```

## 7. Практическое правило

Формулируйте так:

- **Дерево страниц** — где лежит объект.
- **Модель классов** — чем является объект.
- **Page Properties** — какими свойствами и связями обладает объект.
- **Словарь предикатов** — какими типами связей можно соединять объекты.
- **Метки** — как объекты искать, фильтровать и сводить в реестры.
- **Доменные разделы**, такие как `A9. Кредитование`, — не место хранения дублей, а **представления и реестры** канонических объектов.

Такая схема устраняет дублирование, сохраняет единственность объекта и позволяет в Confluence получить практический аналог семантического графа: страница = субъект, строка Page Properties = предикат, ссылка = объект, метки = индексные фасеты.
